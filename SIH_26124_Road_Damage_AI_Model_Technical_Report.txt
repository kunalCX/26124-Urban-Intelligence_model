======================================================================
1. EXECUTIVE SUMMARY
======================================================================

This project uses a custom-trained YOLO26n object-detection model to detect
road-surface damage from images captured or supplied by a public-transport
fleet. The model is intended to become the computer-vision component of the
SIH 26124 urban-intelligence platform.

The final frozen deployment model is:

C:\Users\Kunal Shinde\Desktop\26124-Urban-Intelligence\models\road_damage\v1\best.pt

Model file size:
5,388,229 bytes (approximately 5.14 MiB)

The model was trained for 30 epochs on the RDD2022 road-damage dataset and
validated on 5,757 images containing 8,327 annotated damage instances.

Final validation results:

Overall Precision       = 0.609  (60.9%)
Overall Recall          = 0.521  (52.1%)
mAP@0.50                = 0.559  (55.9%)
mAP@0.50:0.95           = 0.281  (28.1%)

Per-class mAP@0.50:
Longitudinal crack      = 54.7%
Transverse crack        = 57.6%
Alligator crack         = 67.4%
Pothole                 = 44.1%

Per-class mAP@0.50:0.95:
Longitudinal crack      = 29.5%
Transverse crack        = 27.8%
Alligator crack         = 35.8%
Pothole                 = 19.1%

Validation inference time:
4.6 ms/image on the NVIDIA GeForce RTX 3050 A Laptop GPU
(approximately 217 image inferences/second for the inference component alone,
calculated as 1000 / 4.6; real application throughput will be lower because
preprocessing, image transfer, postprocessing, I/O and API overhead also
contribute).

The model is suitable for a hackathon prototype and proof-of-concept. It
should NOT be presented as a certified road-safety or infrastructure-
inspection system. Its main weakness is pothole detection, where recall is
38.6% and mAP@0.50 is 44.1%.

4. DATASET – RDD2022
======================================================================

Training dataset:
RDD2022 – Road Damage Dataset 2022

RDD2022 is a multinational road-damage image dataset containing:

47,420 images
55,007 released training annotations/instances
4 road-damage categories
6 countries:
Japan, India, Czech Republic, Norway, United States, China

The dataset contains road imagery from different acquisition conditions,
including smartphones, cameras, Google Street View imagery and aerial/drone
views.

The four categories used in this project are:

1. Longitudinal crack
2. Transverse crack
3. Alligator crack
4. Pothole

Annotations are bounding boxes.

Why RDD2022 was selected:
- Large dataset
- Multiple countries
- Multiple road environments
- Includes India
- Contains the exact road-damage categories required for this prototype
- Appropriate for object-detection training
- More diverse than a small manually collected dataset

Important limitation:
RDD2022 is not the same as a Navi Mumbai-specific dataset. Therefore,
performance on real Navi Mumbai roads can differ from validation performance.
Local calibration/validation with representative Navi Mumbai images would be
required for a production deployment.

8. FINAL MODEL METRICS
======================================================================

Overall:

Metric                         Value
------------------------------------------------
Precision                     60.9%
Recall                        52.1%
mAP@0.50                      55.9%
mAP@0.50:0.95                 28.1%

Interpretation:

Precision of 60.9% means that, under the validation/evaluation conditions,
the model's detected objects were correct at approximately that rate.

Recall of 52.1% means the model detected approximately half of the annotated
damage instances under the evaluation conditions.

mAP@0.50 of 55.9% evaluates average precision using an IoU threshold of 0.50.

mAP@0.50:0.95 of 28.1% is stricter. It averages AP across IoU thresholds
from 0.50 through 0.95 in increments of 0.05.

Do NOT call mAP "accuracy". Object detection is better described using
precision, recall, IoU, AP and mAP.

13. SEVERITY LOGIC
======================================================================

The current prototype converts model confidence into an application-level
severity label:

Confidence >= 0.70
    HIGH

Confidence >= 0.45 and < 0.70
    MEDIUM

Confidence < 0.45
    LOW

IMPORTANT:

This is NOT a clinically, scientifically, or civil-engineering calibrated
damage-severity model.

It is a prototype rule for demonstrating how an AI detection can be converted
into a prioritized alert.

A production system should determine severity using additional evidence such
as:
- Damage type
- Physical dimensions
- Area/extent
- Depth estimate where available
- Repeated detections
- Vehicle vibration/IMU
- Traffic volume
- Road importance
- Historical observations
- Expert/civil-engineering rules

15. ADVANTAGES
======================================================================

1. Lightweight model

YOLO26n is the nano variant, making it substantially smaller than larger YOLO
variants.

This is useful for:
- Edge devices
- Laptop inference
- Mobile/embedded deployment research
- Fleet-camera applications
- Faster experimentation

2. Fast inference

The project achieved 4.6 ms/image model inference timing on an RTX 3050 during
validation.

This makes near-real-time processing technically plausible on capable GPU
hardware, although complete system latency will be higher.

3. Four directly relevant damage classes

The model directly detects:
- Longitudinal cracks
- Transverse cracks
- Alligator cracks
- Potholes

These are highly relevant to road-condition monitoring.

4. Bounding-box localization

The system does not only say "damage exists."

It identifies approximately where the damage is in the image.

5. Transfer learning

Starting from pretrained YOLO26n weights reduces the need to train a deep
network from random initialization.

6. Multinational dataset exposure

RDD2022 covers six countries and multiple road environments, which provides
more diversity than a small single-city dataset.

7. India is represented

RDD2022 includes Indian road imagery, giving the project some regional
relevance.

8. Integration-friendly

The model is a normal Ultralytics .pt checkpoint and can be called from Python.

It can therefore be wrapped in FastAPI and exposed to a full-stack application.

9. Low model storage requirement

The deployment checkpoint is approximately 5.14 MiB.

10. Scalable architecture

The model can later be moved from laptop GPU inference to:
- Cloud GPU
- Edge GPU
- NVIDIA Jetson-class hardware
- ONNX
- TensorRT
- Other supported deployment formats

======================================================================
16. DISADVANTAGES AND LIMITATIONS
======================================================================

1. Pothole performance is weak

Pothole recall:
38.6%

Pothole mAP50:
44.1%

This means potholes can be missed.

2. Moderate overall recall

Overall recall:
52.1%

A road-monitoring system must consider false negatives carefully because a
missed defect can be operationally important.

3. mAP50-95 is considerably lower

Overall:
mAP50 = 55.9%
mAP50-95 = 28.1%

This indicates that bounding-box localization becomes less reliable under
stricter overlap criteria.

4. Domain shift

RDD2022 is multinational.

The final system targets Navi Mumbai/public-transport conditions.

Differences may include:
- Road construction
- Asphalt type
- Lighting
- Monsoon conditions
- Camera position
- Camera quality
- Vehicle vibration
- Traffic density
- Road markings
- Local repair patterns

Therefore validation performance is not automatically equivalent to Navi
Mumbai field performance.

5. Dataset mismatch

RDD2022 was not specifically collected for the exact camera setup that will
be used by the SIH fleet prototype.

A production deployment should collect and label representative local images.

6. Confidence is not damage severity

A high confidence score means the detector is more confident about its
prediction under the learned distribution. It does not directly mean the
physical road damage is more severe.

7. False positives

The model may sometimes identify non-damage visual patterns as damage.

This can happen due to:
- Shadows
- Road markings
- Repairs
- Image artifacts
- Surface texture
- Unusual lighting

8. False negatives

The model may miss:
- Very small potholes
- Low-contrast cracks
- Occluded damage
- Damage under poor lighting
- Damage blurred by vehicle motion

9. Camera dependency

Performance can change significantly with camera:
- Height
- Angle
- Field of view
- Resolution
- Motion blur
- Exposure

10. No physical depth measurement

The current model detects image appearance. It does not directly measure
physical pothole depth in centimetres.

11. Prototype severity logic

The current HIGH/MEDIUM/LOW system is confidence-based and should not be
represented as an engineering-grade severity assessment.

12. Training cost

The final 30-epoch training run took approximately:

31.154 hours

Therefore frequent retraining is impractical under a tight hackathon deadline.

======================================================================
17. REAL-WORLD METRIC INTERPRETATION
======================================================================

A useful way to understand the current model is:

For every 100 annotated damage objects, the model detects roughly 52 on average
under the validation conditions, based on overall recall.

For the detected objects, approximately 61% are correct according to the
overall precision metric.

However, these are aggregate statistical metrics. They do NOT mean that every
100 real-world road defects will produce exactly 52 detections or that exactly
61 of 100 alerts will be correct.

Real-world performance depends on the deployment domain.

Pothole-specific recall is approximately 39%, which is the main operational
risk for the current model.

Therefore the prototype should use:
AI detection
+
GPS/location correlation
+
human review/verification
+
repeated observations

rather than automatically treating every detection as a confirmed road repair
requirement.

======================================================================
18. MODEL VALIDATION VS REAL-WORLD TESTING
======================================================================

Validation asks:

"How well does the trained model perform on labeled data?"

Real-world testing asks:

"How well does it work on images from the actual intended deployment
environment?"

The current project has strong quantitative validation for the trained
RDD2022 model, but it is still a prototype for Navi Mumbai.

A future field-validation process should be:

1. Collect representative Navi Mumbai road images.
2. Include different times of day.
3. Include dry and wet/monsoon conditions.
4. Include different camera angles.
5. Include different road types.
6. Manually annotate road damage.
7. Split data into train/validation/test sets.
8. Evaluate precision, recall, mAP50 and mAP50-95.
9. Analyze false positives and false negatives.
10. Recalibrate/retrain only if justified by the evaluation.

27. TECHNICAL DEFINITIONS
======================================================================

Precision:
Of the objects predicted by the model, how many are correct.

Recall:
Of the actual annotated objects, how many were detected.

IoU – Intersection over Union:
Measures overlap between a predicted bounding box and the ground-truth box.

IoU =
Area of intersection / Area of union

AP – Average Precision:
Summarizes the precision-recall relationship for a class.

mAP:
Mean Average Precision across classes.

mAP@0.50:
mAP using IoU = 0.50.

mAP@0.50:0.95:
Average mAP over IoU thresholds 0.50, 0.55, ..., 0.95.

GFLOPs:
Approximate billions of floating-point operations for a model pass at the
specified input configuration. It is a computational-complexity indicator,
not a direct measurement of real-world speed.

Parameters:
Learnable model weights. Fewer parameters generally help reduce model size,
although parameter count alone does not determine accuracy.

Epoch:
One complete pass through the training dataset.

Transfer learning:
Starting with an already trained model and adapting it to a new task/domain.

Inference:
Running the trained model on new input data.

False positive:
The model predicts damage where the ground truth does not contain the
corresponding damage.

False negative:
The model fails to detect damage that is actually present.

validated and deployable computer-vision component.

The complete development chain is:

RDD2022
   |
   v
Dataset YAML / class definitions
   |
   v
Pretrained YOLO26n
   |
   v
GPU fine-tuning
   |
   v
30 training epochs
   |
   v
Validation
   |
   v
Precision / Recall / mAP evaluation
   |
   v
best.pt
   |
   v
models\road_damage\v1\best.pt
   |
   v
Inference
   |
   v
Road-damage event
   |
   +-- Damage class
   +-- Confidence
   +-- Bounding box
   +-- Bus ID
   +-- Route
   +-- GPS
   +-- Timestamp
   +-- Nearest stop
   |
   v
FastAPI / Backend
   |
   v
Database + Map + Dashboard
   |
   v
Actionable urban road-condition intelligence

The current model is a technically valid SIH prototype component with measured
validation performance and a clear deployment path. Its main engineering
limitation is generalization to the exact Navi Mumbai operating environment,
especially pothole detection. That limitation should be addressed through
local field-data collection and validation in a future version rather than
being hidden in the presentation.
